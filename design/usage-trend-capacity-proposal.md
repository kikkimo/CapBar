# 总走势容量换算提案（候选估算，待验证）

总走势展示每个绘图区间的**七日额度消耗**。Claude 与 Codex 分别汇总，各自以配置列表中的第一个账号为基准。先算每个账号该区间消耗的七日额度百分比，再换算容量：

```text
基准等效用量 = Σ（账号区间消耗百分比 × 账号七日容量系数 ÷ 首账号七日容量系数）
```

例如 Claude 首账号为 Pro，系数为 1；另一个 Max 20x 账号系数假设为 20。两者各消耗 2% 时，总值为 `2% × 1 + 2% × 20 = 42% Pro 等效`。如果首账号是 Max 20x，同一组消耗相当于 `42% ÷ 20 = 2.1% Max 20x 等效`。纵轴允许超过 100%。不能把不同套餐的原始百分比直接相加。

## 识别方法

| 服务 | 现有自动识别 | 拟增加的细分识别 | 不能可靠识别时 |
| --- | --- | --- | --- |
| Claude | `claude auth status` 的 `subscriptionType`，现有代码只解析这个字段，通常可区分 Pro / Max / Team | 优先检查该账号的 CLI 身份结果是否直接提供细分档位；对 Max，可检查现有授权凭据中的非令牌元数据 `rateLimitTier` 是否明确包含 `5x` / `20x`。只保存识别出的档位，不保存令牌。 | 让用户确认 Max 5x/20x；不能仅凭 `max` 猜测。 |
| Claude Team | `subscriptionType = team`，组织名只用于显示 | 目前没有验证过能从现有探测结果可靠区分 Standard / Premium 座席。后续若发现稳定字段，再自动读取。 | 让用户确认 Standard / Premium；不能仅凭 `team` 猜测。 |
| Codex | `account/read` 的 `planType`，现有代码已解析 | 若接口明确返回 Plus / Pro 5x / Pro 20x，直接映射。现有代码和测试尚未证明它一定返回 Pro 的细分档位。 | 让用户确认 Pro 5x/20x；不能仅凭 `pro` 猜测。 |

以上只是**识别方案**，尚未实测每种订阅的实际返回值。不会为了识别而额外启动 Claude 会话。读取 Claude 授权凭据元数据的步骤只有在明确说明后才执行，不把令牌写入历史数据库或设计稿。

## 拟议的安全显示规则

- 同一服务的所有账号必须拥有已确认的七日容量系数，才显示该服务的完整总走势；缺少系数时显示待校准账号数，并保留单账号走势图。
- 每个区间必须覆盖该服务所有参与汇总的账号；缺测不按 0 处理，曲线在该区间留空。
- 历史数据记录采样时的套餐和容量系数。升级或降级后，历史消耗仍按当时的容量换算，整个图始终使用**当前首账号容量**作为显示单位。
- 显示“Pro 等效”“Team Standard 等效”或“Plus 等效”，避免把叠加值误称为某个账号的额度剩余百分比。
- 如果采用上表未经七日容量验证的候选系数，界面明确标记“估算”，不能把曲线称作精确七日用量。

视觉方案见 [usage-trend-overview-study.html](usage-trend-overview-study.html)。功能分支暂按表中的候选系数计算，并在应用中明确标记“估算”；这些数值仍待七日容量验证。无法细分的套餐由用户在设置中选择具体档位，否则该服务的总走势暂不计算。历史采样保存当时识别或校准的档位；旧记录缺少档位时暂按当前校准档位估算。
